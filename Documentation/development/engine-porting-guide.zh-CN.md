## 摘要

在开始之前，我建议你为已经支持且广泛使用的平台（如 GNU/Linux 或 Windows）编译和运行引擎。修改它，熟悉引擎。

Xash3D FWGS 引擎的一个优点是它的模块化，因此游戏逻辑、UI 和渲染器位于与平台无关的库中。每个库都在运行时加载，可能是可选的也可能不是。例如，如果你的平台没有某种形式的 OpenGL，你可以跳过它并使用我们的软件渲染器！当然，如果你没有任何游戏逻辑，就没有真正的理由运行游戏引擎，因此 Xash3D FWGS 的最小构建是无头专用服务器。

历史上，Xash3D 引擎甚至更加模块化（参见 github.com/a1batross/Xash3D_ancient），但我们认为为了满足跨平台需求，我们将所有平台特定的东西保留在引擎本身中，库必须导入或暴露与平台无关的 API。

好，进入正题！

## 移植指南

这不会是一个完整的教程，因为在一篇文章中涵盖所有内容可能不可能。相反，我将给你关于如何移植引擎、如何将你的移植推送到上游以及如何维护你的移植的提示。

0) 了解你的平台。也许我最近才要求这个，但你**必须了解你的平台**，即它的能力。

目前不支持的配置之一是平台无法加载动态库（`*.so` 或 DLL）。我们无法帮助你，因为支持完全静态的移植以各种方式违反 GPL 许可证。

另一个尚未支持的配置是大端序。

1) 设置工具链。对于初步移植，你可以为自己编写 Makefile，引擎就是这样编写的，所以它**不依赖**任何生成的数据或任何特殊处理。但我建议你无论如何使用 Waf，它与引擎集成得更好且可自我记录。另外，我将只介绍我们的 Waf 构建选项。

2) 打开 `public/build.h` 文件。为你的操作系统和/或 CPU 架构添加适当的检查。这应该不难。

另外，你需要构建 [Half-Life SDK](https://github.com/FWGS/hlsdk-portable/)。它有相同的 `public/build.h`，因此将更改反映到其中。注意为了兼容 HLSDK 专有许可证，它已根据 [Unlicense](https://unlicense.org) 重新许可为公共领域。

我们有一个库命名方案，允许我们和游戏创建者在单个归档中为不同平台分发二进制文件。有关更多信息，请阅读 `Documentation/extensions/library-naming.md`。

简而言之，你需要以独特的方式命名你的平台。对于引擎端，在引擎源代码的 `engine/common/build.c` 文件中完成，对于 HLSDK 端，在 HLSDK 源代码的 `cmake/LibraryNaming.cmake` 和 `scripts/waifulib/library_naming.py` 文件中完成。

你可以使用 [predef 项目 wiki](https://sourceforge.net/p/predef/wiki/Home/) 作为参考。

2) 查看 `engine/platform` 目录。我们通常尝试将所有平台特定的东西放在此文件夹内。

* `platform.h` 头文件中声明了你的平台上必须可用的函数。大多数在无头专用构建中不使用，但我稍后会介绍。

* 符合 POSIX 的（用于 *nix 操作系统）进入 `posix` 子目录。

* SDL 特定代码进入 `sdl` 子目录。注意即使我之前说过平台特定代码在 `platform` 目录中，SDL 显然不是**平台**，所以你可以在整个引擎中遇到 XASH_SDL 检查，通常在输入中。

* *nix 系统的自定义 SWAP 实现在 `swap` 子目录中。当硬件可能没有足够的内存且你无法添加交换内存时使用。我稍后会介绍
它依赖于具有分页内存的系统会将页面加载到 RAM 中并将未使用的移动到通过自定义交换区域 mmap() 的事实。
这允许在具有 MIPS CPU 的音乐播放器、没有 SWAP 支持的 Linux 上运行游戏引擎

* 其他文件夹如 `win32`、`android`、`linux` 等是自描述的。

3) 作为概念验证，你可以尝试测试网络功能和动态库加载是否正确实现。使用 XASH_DEDICATED 或 `--dedicated` 传递给 `waf configure` 构建专用服务器。

启动服务器并尝试从 PC 连接到它。如果一切正常，那么你可以进入下一步。

如果遇到内存不足问题，可以尝试低内存模式，通过 `--low-memory-mode=N` 传递给 `waf configure` 启用，其中 N 为 1 或 2。低内存模式 1 意味着我们**不会**破坏网络兼容性。2 更深入，不保证协议兼容性和可用的多人游戏。当然，使用低内存模式 2 你无法测试你的移植专用服务器。

如果你有任何东西可以编译，现在是提交的好时机。将你的更改提交到 git 并推送到某处（GitHub、GitLab 或你喜欢的），这样你就不会意外丢失它们。

4) 这里是最有趣的部分，构建客户端部分。

有三种可能的情况，按难度递增。

1. 你的平台有 SDL2 吗？如果是，继续编译启用客户端部分的引擎。

2. 你的平台有 SDL1.2 吗？如果是，尝试编译它，但 SDL1.2 支持非常有限且未经过充分测试。

3. 你没有 SDL 并且由于某些原因无法自己移植，或者 SDL 移植对你的平台不稳定？那么你需要实现引擎后端。

如何实现引擎后端？我们有在旧引擎中引入的后端系统。它只是两个文件：仓库根目录 `common` 文件夹中的 backends.h 和 defaults.h。你需要在 `backends.h` 中为你的后端添加宏，并在 `defaults.h` 中定义逻辑。我们已经有一些，查看它们，它们可能对你有用。

完成后，回到 `platform` 目录并打开 `platform.h` 头文件。在 `platform` 文件夹中创建新子目录并开始逐个实现缺失的平台特定后端。由于显而易见的原因，我无法解释这个。你可以使用之前在 `build.h` 中定义的宏来检查你是否正在为你的平台编译，使用 `backends.h` 宏来检查是否必须启用平台特定后端。

完成后，编译引擎，修复错误，提交你的更改并推送到仓库。

记住，如果某些东西不工作而你无法弄清楚为什么，你可以加入我们的 Discord 服务器 discord.me/fwgs。联系我（@a1batross）或其他引擎开发者并附加你的仓库链接，这样我们可以讨论并帮助你进行移植。
